# 项目总结

## 目标

在 FlClash 上建立三个持久、中文、动态更新的策略组，并以独立 Mihomo TUN 服务承担开机后的底层路由，使订阅更新、FlClash 重启或短暂关闭不会永久移除策略能力。

## 最终组成

1. `strategy_manager.py`
   - 读取 FlClash 当前配置和节点。
   - 建立 `净选`、`稳净`、`极速` 及隐藏的 `__谷歌AI`、`__OpenAI`、`__Netflix`。
   - 写入 FlClash 覆写脚本、DNS、规则和健康检查。
   - 建立每节点本机监听器，供互不串线的检测使用。
   - 保存历史样本、分类结果、Google/Gemini 测速和最近状态。
   - 应用新配置后检查连通性；失败时恢复上一份可用配置。

2. `FlClashMihomoService`
   - 由 WinSW 2.12.0 包装 Mihomo 1.19.30。
   - 以 LocalSystem、自动延迟启动和故障重启方式运行。
   - 使用独立端口和 `MihomoSvc` TUN，避免与 FlClash 核心冲突。
   - 将 FlClash 本身的程序流量设为直连，避免双重代理回路。

3. `FlClash-Strategy-20min`
   - 使用 `pythonw.exe` 静默执行，不建立终端窗口。
   - 每 20 分钟更新；登录时也会执行一次。
   - FlClash 在线时同步两套核心；FlClash 离线但独立服务在线时，仍可通过独立节点监听器累积样本。

4. `FlClash-Elevated-AtLogon`
   - 以最高权限在用户登录后启动 FlClash。
   - 取代重复的 HKCU Run 启动项，避免同一进程被启动多次。

5. `FlClash-Google-Observer-20min`（可选）
   - 运行只读的 `google_observer.py`，只写 `managed\google-observer`。
   - 出口以 HMAC 标识，报告不含节点名、出口 IP 与订阅内容。
   - 达到完整性门槛后只产出候选报告，不自动切换真实 Google 流量。

## 已处理的主要问题

- 清除旧覆写后，三个策略组可由脚本稳定重建。
- 扫描质量不足或任一受管组归零时拒绝候选，并恢复最近一次完整非空快照。
- 死锁文件会结合 PID 判断后清理，避免排程永久停止。
- 所有 curl 子进程以 Windows 无视窗标志启动，避免大量终端窗口。
- `稳净` 改为保存 7 天、504 个样本，不再只保留短期样本；216 个样本前维持暂定状态。
- `极速` 与 Google/Gemini 专用组使用按排序的 `fallback`，优先使用管理器排名，同时保留故障切换。
- Google/Gemini 使用专用动态出口池；候选需连续通过搜索无区域重定向、GStatic、账号页及 Gemini 检测，主备优先保持相同出口 IP。
- Netflix 使用固定线路专用组，播放空档时才重钉出口，并按在线率、延迟与 4 小时冷却约束切换。
- Google 或 OpenAI 连接活跃时暂缓热加载；安全套用失败会连同状态、DNS 偏好、独立服务配置及覆写脚本一起恢复。
- 独立 TUN 启用具备状态核对与失败回滚。
- 哔哩哔哩主站、API、图片与视频 CDN 域名固定直连并排除 fake-IP；验收同时检查 7890 代理入口与独立 TUN 访问。
- `maitokens.top` 与 `maitokens.com` 固定直连并使用国内 DoH 解析。
- `__谷歌AI` 与 `__OpenAI` 属可选专用池；候选暂时为空或已不在当前订阅时，自动回退到 `极速`，不阻断一般代理路由或排程更新。
- 国内直连域名的 AliDNS DoH 同样直连，避免海外 DNS 出口返回不适配本地线路的 CDN；Bilibili 的 `bilicdn1.com` 等 CNAME 目标亦纳入同一策略。
- `MihomoSvc` TUN MTU 固定为 1400，避免虚拟网卡 MTU 9000 经 WLAN 1500 时造成 DNS 大响应、TLS 握手及长连接分片异常。

## 当前项目的解读边界

此系统是持续观测和动态决策系统，不是节点品质制造器。供应商拥塞时，它只能在可用候选中选择相对较好者；不能把实际吞吐提升到供应商标称带宽，也不能保证任何外部服务永远不改变风控判定。
